UC_Admin Simulation Module Notes
================================

Purpose
- The simulation module is a standalone game runtime hosted by the UC_Admin framework.
- It is not the framework bot main process.
- A simulation is instantiated as an object and controlled through run() and exit().
- The module may use existing framework tools such as Logger, DatabaseManager, NetworkManager, and scheduler utilities when needed.

Current Runtime Contract
- SimulationEngine is the primary runtime object.
- run() starts the simulation.
- exit() stops the simulation.
- Shutdown is owned by the simulation itself.
- The dungeon game object can be created in admin mode for faster no-clip movement and full-map visibility.
- The framework crash manager is not responsible for simulation crashes.
- If either simulation thread crashes, SimulationEngine logs the crash, calls the game crash hook, and shuts itself down.
- The engine owns exactly two simulation-managed threads:
  - UC-SimulationRender: creates the simple GUI and runs the update/render loop.
  - UC-SimulationInput: receives queued keyboard and mouse events and dispatches them to blank game hooks.
- Java GUI libraries may create their own internal platform threads, but the simulation module itself manages only the two threads above.

Logging Contract
- Simulation log codes are separate from the framework bot code registry.
- Simulation codes start with A0 followed by a three-digit issue number.
- Example: A0001.
- Use Logger.log with the same style as QueueManager:
  - SYSTEM for start/stop/lifecycle events.
  - INFO for successful meaningful operations.
  - DEBUG for low-level loop or state breadcrumbs.
  - WARN for survivable abnormal conditions.
  - ERROR for crashes and failed stop/start behavior.
- Use Logger.logDump for crash forensics and large diagnostic payloads.
- Keep simulation code meanings in SimulationCodes.txt, not src/main/codes.txt.

Input Contract
- Key and mouse listeners exist as templates.
- Current input hooks are intentionally blank.
- Future behavior should be added through SimulationGame methods:
  - onKeyPressed
  - onKeyReleased
  - onKeyTyped
  - onMousePressed
  - onMouseReleased
  - onMouseMoved
  - onMouseDragged

Game Design
- The game is a 2D dungeon exploration game.
- Dungeon generation is seed-based.
- The same seed should generate the same dungeon.
- Non-admin players can only see geometry inside line of sight; walls and sealed openings block visibility.
- Non-admin visibility should stay clear near the player and darken with distance.
- Wall light items can reveal nearby line-of-sight areas when the player is close enough to notice the light.
- The dungeon is assembled from handcrafted artifact templates.
- The generator chooses which artifacts to place, how they connect, and how they rotate.
- Artifact geometry is manually defined; generation does not invent raw room geometry.

Artifacts
- Artifact templates are master definitions.
- Templates never move, rotate, or change.
- Artifact instances are placed copies of templates.
- Instances store world position, rotation, and vertical mirror state while referencing their template.
- All template coordinates are relative to artifact center (0,0).
- Only four rotations are supported: 0, 90, 180, and 270 degrees.
- Rotation is handled by instances using coordinate swapping/sign changes.
- Generation may mirror artifact instances across the artifact's vertical centerline to reuse one-sided connector geometry.

Artifact Data
- Walls are line segments.
- A wall has a start coordinate and an end coordinate.
- Walls define collision and visual structure.
- Walls do not define dungeon connectivity.
- Openings are separate from walls.
- An opening has a center position, direction, and width.
- Openings are the connection points between artifacts.
- Occupied areas are separate from walls and openings.
- Occupied areas are polygons describing the physical space consumed by the artifact.
- Rectangular occupied areas are stored as four-point polygons.
- Occupied polygons are used for overlap checks.
- Floor space is not stored directly.
- Valid floor locations can be derived from occupied space minus walls and other blockers.

Generation Process
- Select an existing artifact.
- Select an unused opening.
- Choose a compatible artifact.
- Rotate and optionally mirror the new artifact appropriately.
- Align the new artifact opening with the existing opening.
- Check rotated and translated occupied areas for overlap.
- Place the artifact if valid.
- If no continuing artifact can be placed from an opening, a one-opening artifact may be placed as a dead-end cap.
- Nearby unconnected openings may be reconnected with a bounded connector search before final open walls are sealed.
- Reconnection should primarily use connector artifacts and hallway artifacts, including straight, offset, and L-shaped hall pieces.
- Continue indefinitely to support an infinite dungeon.

Future Editor
- Artifact definitions should eventually be created through an artifact editor.
- The editor should behave like a simple paint program for drawing artifact geometry.
- The editor exists to avoid manually editing large coordinate lists in source code.
- The artifact editor is the first major simulation tool to build before gameplay.
- The editor is its own object/runtime with run() and exit(), separate from the game runtime.
- The editor should overlap with the game runtime structure as closely as practical.
- The editor owns two editor-managed threads:
  - a GUI/render thread
  - an input dispatch thread
- Artifact data is saved through DatabaseManager, not by direct file I/O and not by using BatchManager or QueueManager directly.
- Artifact storage path is database/artifacts/artifacts.json.
- The central artifacts JSON should store all artifact templates by id/name.
- The editor supports saving artifacts and loading existing artifacts by id or saved name.
- The canvas is a gridded pixel canvas, initially around 200 by 200 cells.
- The user manually places the artifact center.
- Saved artifact geometry coordinates are offsets from the selected center.
- Editor controls should include scroll-wheel zoom, right-click drag pan, and left-click drawing.
- The editor should show a small controls strip along the bottom.
- Pressing R rotates the preview by 90 degrees without changing saved template geometry.
- When preview rotation is active, editor input should map clicks back into template coordinates so drawing and erasing line up with the rotated display.
- Pressing X toggles between eraser and the previously selected non-eraser tool.
- Tools should include select, center, wall, opening, occupied area, item placement, and eraser.
- The select tool should select every editable element inside or intersecting the selected rectangle.
- Ctrl+C copies the current selection into an editor-session clipboard.
- Ctrl+V pastes the clipboard near the current cursor position.
- The editor-session clipboard should persist across loading or creating artifacts, but clear when the editor exits.
- Wall drawing uses first point then second point, with a preview while the mouse moves.
- Occupied area drawing supports two modes.
- Dragging with the occupied tool creates a rectangular occupied polygon.
- Clicking with the occupied tool places polygon points.
- Clicking the starting polygon point closes and saves the occupied polygon.
- Occupied areas are saved as a list of points.
- Older occupied rectangle saves should still load by converting start/end corners into a four-point polygon.
- Opening drawing uses first click for position and second click for direction.
- Inactive layers should stay visible but faded and non-interactive.
- The editor may allow invalid artifacts but should warn on save.
- The editor should reject saving artifacts named default because that name is reserved for the generator bootstrap artifact.
- Undo and redo should exist from the first editor pass.
- Ctrl+Z and Ctrl+Y should trigger undo and redo.
- The eraser should remove walls by touching any part of the wall segment, occupied areas by clicking inside the area, center/opening dots by proximity, and placed items by cell.
- Editor action buttons should live at the bottom of the side panel so more tools can be added above them.
- Items are placed on cells/blocks, not grid intersections.
- Item templates are selected from a small static item library by id.
- The first item is wall_light.
- Wall lights can only be placed on a cell touching a wall.
- Wall light direction is assigned automatically from the touched wall and saved with the item.
- Runtime wall light positions are cell coordinates; draw and ray origins should use the cell center, not the grid intersection.
- The visible wall light box should sit inside its cell while touching the cell edge opposite its facing direction, which is the wall side.
- Artifact JSON stores items as id, position, and direction.
- Runtime artifact loading should preserve item id, position, and direction and transform them with the placed artifact.
- Artifact templates should include a numeric category.
- Category 0 is reserved for forced/non-random artifacts and should never spawn through normal generation.
- Categories describe artifact roles such as basic hallways, exotic hallways, rooms, chambers, junctions, dead ends, connectors, and setpieces.
- Generation profiles use artifact categories together with derived geometry/opening metadata to decide what can spawn next.
- Artifact loading should be backward-compatible with older artifact JSON versions.
- When a new save uses a name that already exists, the editor should ask before overwriting.
- When a loaded artifact is renamed and saved, the old name lookup should be removed.
- Loaded artifacts can be deleted from the central artifact JSON.

Future Systems
- Interactables, lighting, darkness, enemies, loot, spawn locations, decorations, and similar systems will be built on top of artifacts later.
